# SideTap

LLM agents drive a real iPhone from Windows over USB + WebDriverAgent (go-ios).
Windows rebuild of ShawnPana/phone-harness (which is macOS-only).

## Architecture

- `src/phone_harness/wda_client.py` — thin HTTP client for WebDriverAgent (:8100). requests only. Each client owns ONE persistent `requests.Session` (`self._http`) so the loopback connection to WDA stays warm: the module-level `requests.request` builds and closes a throwaway Session per call, and every helper funnels through `_request`, so a per-call TCP connect was paid on every tap, read and screenshot. Anything monkeypatching the transport must patch `requests.Session.request`, not `requests.request`. `find_first`/`element_clear`/`element_value` are the ONLY element-id lookups in the codebase: `set_field_text` clears and reads back a field, and `current_page()` reads one attribute off one element. There is deliberately NO `active_element()` and adding one back is a bug: `GET /element/active` answers a Messages thread with a message BUBBLE (`XCUIElementTypeTextView` named `CKBalloonTextView`) while the caret is blinking in the compose bar, so the field clear ran on a message — which is a LONG PRESS, and that is what popped the Tapback picker open mid-send — and the read-back returned the message's text, so `send_message` refused what it had correctly typed (2026-08-12, docs/ERRORS.md). Resolve the field you mean with a bounded class chain instead (`helpers._field_element`). Perception stays on `/source`. A BOUNDED type query is cheap (`**/XCUIElementTypePageIndicator` + value = 0.37s against 3.0-5.7s for a Home Screen `/source`), but an UNBOUNDED one is not merely slow — `**/*` on the Home Screen KILLED WDA outright and took the session with it (2026-08-12, docs/ERRORS.md). `find_first` returns one id and never a list so it cannot quietly become a perception path. Kill switch: a `.state/STOP` file blocks every action POST at the `_request` chokepoint (perception GETs keep working). The same chokepoint appends every successful action POST to `.state/agent_activity.log` (bounded ring; typed text NEVER recorded, only char counts — it can be a passcode). WDA holds exactly ONE session and creating a new one evicts the holder, so every client shares the id published in `.state/wda_session`: adopt it, heal an unusable id by adopting the replacement or minting fresh. "Unusable" covers "invalid session" AND the `point.x != INFINITY` state — a session that crosses a screen lock keeps answering GETs but fails every /actions forever (bit the Unlock button live; a test pins the heal). That heal can only fire on an error it SEES, and the poisoned session HANGS ~16.2s before it answers at all: any client whose timeout is shorter gives up first, so it healed nothing and every later gesture timed out again, forever. The shortest-timeout client is the human-facing one — `viewer.py`'s `Handler.client` is `timeout=10`, and it serves every tap, swipe and keystroke (reproduced against a fake WDA that hangs: tap #1 failed at 10.01s, tap #2 at 10.02s, unchanged forever; 2026-08-14, docs/ERRORS.md). So `requests.Timeout` raises `WDATimeout(WDAError)` and an `/actions` timeout marks the session for replacement on the NEXT gesture (0.02s). GESTURES ONLY — a poisoned session still answers reads, and re-minting per read would churn the one session WDA allows. The timed-out gesture is NEVER replayed: a timeout does not cancel it, the swipe may still be landing, and a replay double-taps (a test pins both halves). That heals the second gesture; the FIRST one still paid the hang, so a gesture that follows `_SLEEP_SUSPECT_SECONDS` (30s) without this client landing one mints UP FRONT instead. The poison is a display-WAKE phenomenon, not a lock: measured on device 2026-08-14, a real tap on the still-dark screen answered in 0.59s and the gesture right after the wake hung 16.25s, while a fresh session was 0.01s and its swipe 1.18s — and nothing cheap separates the two, since /status, /wda/locked and orientation all answer in ~0.01s either way. The clock counts ONLY LANDED GESTURES: keyed on "any action" it was the `press_button("home")` that wakes the display which refreshed it, so the rule sat there doing nothing on the exact sequence it exists for (caught by running it live, not by the green suite; a test pins it now). The session creator applies the post-gesture waits from config (WDA_IDLE_WAIT=2, WDA_ANIM_COOLOFF=0 — the cool-off default of 2 cost 2-5s per swipe under scroll momentum; ~0.7s with it at 0, measured on device). That POST is still best effort — a session on default waits is slow, not broken — but it now carries seven keys the live view and every gesture wait ride on, so the `except WDAError` PRINTS the miss to stderr instead of passing in silence: an un-tuned session is indistinguishable from "the viewer is laggy today" and leaves nothing to grep. It is deliberately NOT `log_event`, which is the activity feed for things that MOVED the phone (the wedge recovery's Home press) — this moved nothing, and a warning in that ring would read as a gesture nobody made. It is also the line that will name an older WebDriverAgent rejecting the whole settings call over `accessibilityDeadline` (WDA_ACCESSIBILITY_DEADLINE, appium/WebDriverAgent#1214, 0 disables the key entirely). That same settings dict now also carries `maxTypingFrequency` (`config.WDA_TYPING_FREQ`) and the three MJPEG keys. Typing rate is where a long paste actually goes — `/wda/keys` is ONE request from here and `len(text)/rate` seconds on the phone — but the default is WDA's own 60, i.e. a deliberate no-op until it is measured, because raising it fails QUIETLY: iOS drops synthesised keystrokes above some device-specific rate, `set_field_text` reads back, and `send_message` then refuses a message that typed wrong, so an over-aggressive rate turns into refused sends rather than a visible error. The MJPEG keys are there because settings ride with the session and `_create_session` never applied them, so every mint — the 30s-idle remint, `unlock()`, an eviction heal — dropped the live view to WDA's defaults until the viewer's next 5s `/api/status` tick called `configure_mjpeg`; that call stays, for a session this process ADOPTED rather than created (a test pins both, and pins that an adopter still sends no settings at all). `config.WDA_ACCESSIBILITY_DEADLINE` (2.0s) rides in the same dict and does NOT bound the snapshot: appium/WebDriverAgent#1214 bounds a run-loop RESPONSIVENESS pre-check — before a snapshot proceeds WDA confirms the target app's main loop is answering, and only that confirmation must land inside the deadline, after which an unresponsive app is aborted with 'illegal/unresponsive application state' instead of hanging with no upper bound. So a 2.0s deadline against a 3.0-5.7s Home Screen `/source` truncates nothing — the Home Screen is slow because the tree is big (554-610 nodes, 244 KB), not because springboard stopped answering — and the number that matters is not the read's duration but how long a busy-but-working app takes to confirm its run loop; upstream ships it DISABLED, and 2.0 here is the deliberate opt-in bound on the TikTok wedge. `orientation()` is the cheap guard for anything memoising `window_size()`: 7.7ms against 201ms (measured 2026-08-14). The gap is NOT session overhead — session routing is FREE (`GET /session/{id}` is 4.2ms and `/session/{id}/orientation` 7.7ms) — it is that `/window/size` resolves the ACTIVE APPLICATION's frame and orientation does not; `wda/activeAppInfo` (102ms) and `wda/screen` (295ms) pay the same tax. So the rule is avoid calls that RESOLVE THE ACTIVE APP, never "avoid session-scoped calls" — that theory was measured dead. Being a `_session_request` is load-bearing twice over: it heals an evicted session like any other call, and it raises `WDAError` when WDA is gone, so a caller serving a memo can still tell a live link from a dead one. `tap(x, y, hold_ms=None)` resolves `None` to `config.WDA_TAP_HOLD_MS` (80, the shipped literal, so nothing changes until it is measured): the scripted contact is pure wait and roughly 20% of a bare tap budget, but a contact that is too brief is DROPPED and a missed tap is worse than a slow one, so a caller that cannot afford a miss pins its own value rather than riding a knob someone may tune down — `helpers._enter_passcode` passes 80 explicitly, because a wrong or dropped pad tap burns an iOS lockout attempt. `long_press`'s pause IS the gesture (viewer.html's ring is timed against it) and `swipe`'s 40ms pre-move hold is measured; neither takes the knob. Both pasteboard calls run inside `_runner_foreground()`: iOS 16+ only lets the FRONTMOST app touch UIPasteboard, so a bare `setPasteboard` answered 200 and set nothing (text had been silently broken that way; measured 2026-09-03, docs/ERRORS.md). The dance activates the runner (`runner_bundle()`: `.state/wda_bundle` or `WDA_BUNDLE_ID`, a file read and never go-ios), makes the call, re-activates the previous app or presses Home, and sleeps `_HANDBACK_WAIT` (1.0s, measured) for it to be frontmost — a FIXED settle and never a poll of `activeAppInfo`, which resolves the active application and is the hang class: the first version polled it up to 20 times per clipboard call and 8 of the 10 wedge recoveries the watchdog ever logged landed that afternoon — with `waitForIdleTimeout` at 0 for the duration, restored in a finally, because the runner's own screen never goes idle and the activation ran 17-18s on the shared session's WDA_IDLE_WAIT (0.09s at 0). `set_clipboard` takes bytes with `content_type="image"` and `get_clipboard_image()` reads PNG bytes back; that is what `helpers.send_image` (caption via `text=`, sent as a second bubble by iOS), `helpers.save_clipboard_image`, and the viewer's Ctrl+V / Send image / Copy phone image paths ride on. `save_clipboard_image` marks the session tainted like any read, so a `send_image` in the same process then waits on the approval card — that wait looked like a WDA hang once (2026-09-03) and was not.
- `src/phone_harness/trust.py` + `approval.py` — prompt-injection defense. `trust` holds the sticky process taint flag (set by `ui_tree`/`screenshot`/`read_messages`; `trust.internal()` keeps a helper's own bookkeeping reads from counting), the heuristic scanner (flags are a SIGNAL for the human card, never an allow/deny — no filter detects injection reliably), and the data-not-instructions envelope the MCP layer wraps screen reads in. The envelope pays the full 48-word `WARNING` only when the scanner actually flags something; a clean read carries `WARNING_SHORT` instead, because the model already has the same rule in the server instructions and in every read tool's description, and the full text nested once per batched step inside `act()`, which exists to cut cost. Shorter, never silent: the scanner has false negatives, so a clean read still says the content is data. `approval` is the `.state/pending_send.json` handshake that blocks `send_message` until the viewer answers; fail closed, timeout means deny, one card at a time. `approval.mode()` is the always/flagged/off setting, read at SEND TIME (not import) because the human flips it mid-session in a different process: `.state/send_approval` (viewer toggle) beats `SEND_APPROVAL` in `.env`, and anything unrecognized falls back to `always` — a setting that cannot be read must never be the one that disables the gate. `set_mode` is deliberately absent from `_TOOLS`, `_ACT_TOOLS` and `helpers.__all__`, and a test pins that. `send_message` gains NO bypass argument on purpose — every parameter of an MCP tool is reachable by an injected instruction — so the viewer's own `/api/text` uses the thread-local `trust.human_initiated()` instead (it also holds `_ACTION_LOCK`, so gating there would freeze every viewer gesture for the whole timeout). `type_text` refuses PHONE_PASSCODE; `unlock()` drives the client directly and is unaffected. The MCP reading tools must be registered AFTER their `__doc__` is extended: FastMCP reads the docstring at registration, not at call time.
- `src/phone_harness/device.py` — go-ios wrapper; detached tunnel/runwda/forward processes, pids+logs in `.state/`. `ios_path()` falls back to `%APPDATA%\npm\ios.exe` when PATH lookup fails — Windows truncates a >4095-char registry PATH in the logon environment, so shortcut/Startup launches can miss the npm dir (bit the Startup shortcut live; a test pins the fallback) — and then to `%LOCALAPPDATA%\SideTap\bin\ios.exe`, where `site/install.ps1` puts go-ios on machines that never had Node/npm (a test pins this one too). `detect_wda_bundle()` caches its hit in `.state/wda_bundle` because deep sleep EMPTIES `ios apps --list` while the app is still installed (seen live); `lockdown_ready()` (`ios date` exit code) is the "has the human woken the phone" probe — deep sleep gates lockdown (ReadPair errors) while tunnel services keep working. `start_tunnel()` no longer sleeps a flat 3s just to see whether the tunnel process died: it polls `tunnel_running()` — the readiness predicate that already existed, true only for an entry carrying BOTH an address and an rsdPort, i.e. the RSD handshake the very next step (`ios image list`) dials — and returns the moment it confirms, so a healthy machine stops paying 3s in front of the DDI mount, the WDA launch and the WDA poll on every cold bring-up, every viewer Restart click and every deep-sleep self-heal, exactly the moments the header reads "Starting link…". The early return must gate on `tunnel_running()` and nothing weaker: returning on "the process is still alive" hands a half-established tunnel to `ddi_mounted()` and reads as a spurious "developer image not mounted", and `_up()` already proceeds straight to `ddi_mounted()` with zero settle whenever `tunnel_running()` is true, so the poll makes no claim the codebase does not already make. `_TUNNEL_READY_TIMEOUT` (3.0, UNMEASURED — nobody has timed a userspace tunnel, so the cap stays at the sleep it replaced and the worst case is unchanged) and `_TUNNEL_READY_POLL` (0.5, coarse because each probe is a ~207ms process spawn even though `tunnel ls` is an HTTP query to the local go-ios daemon and never touches the phone) are named constants for a one-line revert. `tunnel_running()`'s optional `timeout` is load-bearing, not decoration: it runs `_run(["tunnel","ls"], timeout=10)`, so a probe started at t=2.9s would run to 12.9s and stretch that cap fourfold — each probe is handed only the budget that is left, and a test recomputes that from a scripted clock. `admin.py` is deliberately untouched; both other callers keep the 10s default. `ddi_mounted()`/`mount_ddi()`: an iOS UPDATE silently unmounts the Developer Disk Image, and without it testmanagerd refuses every test session — runwda dies in dtx channel timeouts that look like a broken tunnel (bit live 2026-08-10); mounting needs the phone UNLOCKED (DeviceLocked otherwise), so `up()` auto-mounts and the doctor names it. `list_apps()` persists a non-empty result to `.state/apps_cache.json` and falls back to it when the live `ios apps --list` comes back EMPTY — the same deep-sleep failure mode `detect_wda_bundle` already caches around; a live non-empty result always overwrites it, so a newly installed app stays findable. It lives INSIDE `list_apps()`, so `helpers.open_app` and admin both inherit it with zero changes, and it fixes the live bug where `open_app` raised "Unknown app" for an installed app after deep sleep. `memoized_run()` scopes `list_devices()`/`list_apps()`/`_netstat_ano_lines()` to ONE caller-defined block (one ~4s doctor pass) so the same 207ms spawn is not paid twice — backed by `threading.local()`, NEVER a module global: `viewer.py` runs a `ThreadingHTTPServer` plus `_heal_loop` and `_refresh_lan_state`, and with a shared global two overlapping blocks stomp each other's restore and leave a non-None dict frozen for the life of the process after both have exited (a frozen empty `list_devices()` makes `up()` and the viewer's Restart button report "No iPhone found" forever while the doctor panel shows the phone connected). Nothing survives the block, because a stale check is a lying check. Two independent adversarial reviews caught it 2026-08-14; a test pins the thread isolation. `foreground_springboard()` (`ios launch com.apple.springboard`) is the ONLY escape from a WEDGED WDA and it exists because an app can hold WDA hostage: in TikTok's For You feed every call that RESOLVES THE ACTIVE APPLICATION — `/actions`, `/wda/activeAppInfo`, `/window/size`, `/source` — can block with no upper bound, and since WDA serves requests ONE AT A TIME the whole agent stops behind it (`/status` timed out for 321s straight, and `:9100` refused too, so the viewer goes DARK; measured 2026-08-17, issue #2, docs/ERRORS.md). AX-free calls are instant only BETWEEN hangs (`/status` 0.004s, `/screenshot` 0.22s, `/orientation` 0.01s on the same screen) — while a call is actually stuck they queue behind it too, so NOTHING answers and silence is the only symptom (tqninh, 4/4 on a second device: post-wedge `/status` AND `/screenshot` both timed out at 10s). That is why `link_state()` reads a wedge as socket-accepts-plus-silence and never as a probe that still answers. It is a HEAVY TAIL, not a hard block — the same screen answers in 0.08s or never (warm app 0.08-1.1s, 0/3 wedged; cold 2.9-5.5s, 1/3), and the rate collapsed to zero in 28 swipes once the app settled — so anything measured against it MUST re-run its control: a `snapshotMaxDepth` cap looked like a cure until the default-depth control also stopped failing (retracted, see ERRORS.md). Restarting is the wrong repair AND it fails — the stuck runner is still on the phone, so the new one dies with XCTest error 103, which reads as an expired signature and cost a reporter a whole Sideloadly re-sign. `waitForIdleTimeout=0` does NOT prevent it (a different wait), `enforceCustomSnapshots` makes it worse, and pinning `defaultActiveApplication` only postpones it (swipe 1 returned in 24.4s, swipe 2 wedged permanently) — all measured, do not retry them. Nothing in WDA can bound it: no gesture route skips app resolution, and `snapshotTimeout`/`customSnapshotTimeout` were removed upstream in appium/WebDriverAgent#970 (filed as their #1210).
- `src/phone_harness/admin.py` — `doctor` (ordered checks, each names its fix; the STOP kill switch is checked FIRST, then LAN exposure and the 7-day signature countdown), `up` (serialized by `_UP_LOCK`: launch.py's background bring-up and the viewer's Restart link can overlap; `bringing_up()` reports that lock so the viewer can say "starting" instead of "broken"), `down`, `notify-expiry` (Windows toast when <36h remain on the signature; `--install` registers a daily 10:00 scheduled task via phone-harness.cmd — renewal itself always needs one Sideloadly click, Apple auth mints the profile). `doctor_results()` wraps its CHECKS loop in `device.memoized_run()`, so `ios list`, `ios apps --list` and netstat each spawn once per pass instead of twice (~500-700ms at the measured 207ms spawn floor, and the viewer re-runs doctor ~6 times in the first minute of every boot); the memo dies with the pass, so a second run never reports stale state. `_up()`'s WDA poll is `_wait_for_wda(client, deadline, interval=0.25)`: `is_up()` is a 3.8ms `/status` probe, so the old 2s sleep wasted up to 2s per iteration on every launch, Restart-link click and deep-sleep self-heal; deadline and give-up behaviour are unchanged, and the progress dot is throttled so the faster interval does not flood the log. `_up()` asks `WDAClient.link_state()` (up / wedged / down) instead of a bare `is_up()`, because a WEDGED link — socket accepts, nothing ever answers, an app holding WDA's serial loop hostage — is repaired by `device.foreground_springboard()`, NOT by a restart that cannot even land (see device.py). It tries that first, and only a link that is genuinely DOWN reaches the restart path; the doctor names the wedge the same way. The failure tail no longer prescribes Sideloadly when the profile on disk is still valid, and never after a wedge — that hint sent the reporter of issue #2 through a full re-sign with 6 days left on a good signature. `_check_signature` PASSES during the countdown and fails ONLY once the signature has actually expired. Input works the whole 7 days, and by the note above nothing can renew it early, so failing at <48h left reddened the header, counted as "1 check failing", auto-opened the overlay and raised the amber banner (viewer.html keys it off `!sig.ok`) for two days over a working system — while its own fix line read "No click can extend it early". A check that fails while the thing works is the same lying-status bug as a green over a dead link, pointed the other way. The countdown stays visible in the viewer's Phone pane, which renders that detail whatever `ok` is, and `notify-expiry` still toasts under 36h.
- `src/phone_harness/syslog.py` — rolling capture of the phone's own log, for appium/WebDriverAgent#1210: the maintainer's one ask was device syslog captured ACROSS a wedge. The wedge cannot be scheduled (every call or two for ~20 minutes after TikTok was installed, then not once in 28 swipes the same night), so the capture runs the whole session — but `ios syslog` streams ~27 KB/s (1.79 MB in 67s, measured), which is ~100 MB/hour of disk for noise. So the stream is a RING in memory (`RING_LINES` = 20k ≈ 110-220s at the 90-180 lines/s measured on device) and reaches disk only when `mark()` is called. The ring must outlast the DETECTION delay, not the event: `viewer._HEAL_MIN_SILENCE` is 45s, and the log worth reading is from when the app stopped answering, already 45s+ in the past by then (a test pins that ratio). `admin._unwedge` marks BEFORE it presses Home, because the repair ENDS the occurrence — a mark after the press captures only the recovery (a test pins the ordering), and `TAIL_SECONDS` (45s) keeps recording so the recovery lands in the same file. `_plain()` strips go-ios's `{"msg": ...}` wrapper and its own `module: go-ios` chatter, so the dump is plain syslog someone else can read. The viewer runs `start()` on its OWN 60s loop (`viewer._syslog_loop`) — idempotent, so the same call restarts a capture that died with the tunnel, which deep sleep does routinely — and NOT as a line inside `_heal_loop`: `start()` reads the clock and can spawn a subprocess, while `_heal_loop` is driven in tests by a scripted `monotonic()` over the real `time` module, so sharing the loop ate one scripted tick per pass. That was invisible locally (go-ios present, so the first call spawned a capture and every later one early-returned) and turned CI red where go-ios does not exist — and it meant a plain unit-test run spawned `ios syslog` against the phone. A source-scan test pins the separation, because the symptom only ever surfaced in the other module's tests. `_RETRY_SECONDS` (120s) stops a phone that is simply asleep from respawning it every pass. `start()` clears an orphan first via `device.stop_all(("syslog",))`: a viewer killed with taskkill /F (no `/T`, deliberately — see viewer.py) leaves its `ios syslog` child blocked forever on a pipe nobody reads, still holding a syslog relay, one per viewer restart. A CLI-only run never starts the reader, so `mark()` returns None there rather than writing an empty ring, which would read as "the phone said nothing". The dump names itself in the viewer's Activity feed and lands in `.state/`, which is gitignored — deliberately no download button: the human's next move is attaching it to a GitHub issue, outside the viewer either way. Its header warns before sharing, because a device log carries the device name, installed bundle ids and whatever any daemon logged.
- `src/phone_harness/capture.py` — screenshots. Prefers WDA's HTTP `/screenshot` (sessionless client, cannot steal the one WDA session) with a 10s back-off; falls back to the `ios screenshot` subprocess, which is the only path that works before signing.
- `src/phone_harness/photos.py` — camera-roll pull over AFC (pymobiledevice3, the dependency signing.py already carries). NEVER touches WDA: no session, no gestures, so it must never take the viewer's `_ACTION_LOCK` — a first pull of a full roll runs minutes, and holding that lock would 409-drop every human tap for the duration, which is why viewer.py runs it as a `_PHOTO_JOB` background thread (same shape as `_FIX_JOB`) and the page polls `/api/pull-photos`. Incremental with NO state file: DCIM subfolders are mirrored under the dest (`PHOTOS_DIR`, default `~/Pictures/iPhone`), name-exists = skip — mirroring is what makes iOS's IMG_XXXX rollover collision-free, so don't flatten. Each file lands via `.part` + rename or a killed pull leaves a truncated photo that "exists" and is skipped forever. pymobiledevice3 10.x mixes sync and coroutine methods on AfcService (probed live 2026-09-01: `listdir` answers plain, `pull` is a coroutine), so every call goes through `_aw()` instead of guessing per method; `afc.pull` streams >4MB files and preserves mtimes, which is why it is used per file instead of `get_file_contents` (a 4K video in memory). Verified live: 584 files/1.7GB pulled, second run 0 pulled/584 skipped.
- `scripts/lock_ports.ps1` — self-elevating firewall rule blocking LAN access to :8100/:9100 (WDA has no auth). Fired by the viewer's Lock ports button or run by hand.
- `src/phone_harness/signing.py` — `fix-input`: builds a p12 from Sideloadly's cert, reads the profile Sideloadly minted back off the phone, re-signs WDA incl. the nested `.xctest` via `ios sign app`. All local; no Apple auth. The captured/supplied profile lands in a `.pending` staging file and is committed to `.state/profile.mobileprovision` only AFTER `ios sign app` succeeds — the doctor's countdown reads that file as "what is on the phone", so committing first turned a failed re-sign into a fresh 7-day PASS over the old dying signature (adversarial review 2026-08-13). Same review: `fix_input` catches `subprocess.TimeoutExpired` (openssl 30s, sign 300s) and returns ok:False instead of letting it kill the viewer's worker thread. Renewal truth (proven 2026-08-14, account-appids.json NearestTtl unchanged by a fresh sign): NOTHING moves the expiry mid-week — Apple pins every re-sign, Sideloadly included, to the App ID's original 7-day window. The countdown resets only with the first sign AFTER expiry, so the countdown check and the toast deliberately do NOT prescribe fix-input until it has expired (a mid-week Sideloadly Start is worse than useless: its bare install breaks WDA with error 103 until a local re-sign, which bit twice on 2026-08-14). Capture windows default to 600s — 180s lost a race to the human+Sideloadly loop. `fix_input` opens with the SideTap Pro seam: `_pro_provider()` reads `SIDETAP_PRO_PATH` from `.env`, puts it on `sys.path` and imports `sidetap_pro` (private repo github.com/ucsandman/sidetap-pro — 1-year signing with the user's own Apple developer account). Contract: `identity_for(udid, progress)` returns None while pro setup is incomplete (fall through to the Sideloadly flow, unchanged), `(p12_path, p12_password, profile_bytes)` when ready (both Sideloadly steps skipped, same pending/commit staging), and raises when configured-but-broken — reported verbatim, NEVER a silent downgrade to 7-day signing. A profile argument alongside an active pro install is refused (mixed teams); an import failure prints to stderr and falls back (a broken pro install must not brick the open core). tests/test_signing_pro.py pins all five directions with a fake module in sys.modules. The profile is read off the PHONE, never watched for on this PC, and the watcher it replaced (`scripts/watch_profile.ps1`, deleted 2026-08-16 — do NOT bring it back) is why: Sideloadly 0.60 signs IN MEMORY and streams the IPA to the device, so no file is ever written to watch for. Meanwhile the session id changes on every 30s-idle remint and every `unlock()`, so keying on it paid the full 201ms `/window/size` for a size that cannot have changed — outside `_ACTION_LOCK`, microseconds before the user's next tap. `_TUNED_SESSION` stays keyed on the session, because MJPEG settings genuinely ride with it. `/api/status` also answers `link` ("up" / "wedged" / "down") beside `input`, and viewer.html hides the "Fix input" re-sign wizard on `link === 'wedged'`: a wedged link BY DEFINITION proves the signed runner is on the phone (the socket accepted), and prescribing a full Sideloadly re-sign there is what cost issue #2's reporter a re-sign with 6 days left on a good signature. The split costs zero extra WDA calls — `_request` already raises `WDATimeout` for accepts-then-silence and a plain `WDAError` for refused, and both already reached this handler's `except`, so it is an `isinstance` on an exception it was catching anyway; no probe and no doctor call, because this endpoint runs every 5s and must stay at one 7.7ms `orientation()`. "Restart link" (btn-up) is deliberately still unconditional on any failure — `POST /api/up` unwedges before it restarts, so it is the repair for BOTH states, and hiding it is the regression this change could have introduced (a source-scan test pins that it reads `hidden = inputEnabled` with no wedge clause). Do NOT extend the rule to an 'unsigned' state keyed on the doctor's `sig.ok`: `_check_signature` returns ok:true both when no profile was ever captured and for the whole countdown, so that would hide Fix input from a genuinely expired machine. Beside it rides `silent_for` — the AGE of `_HEAL["down_since"]`, never the raw monotonic stamp, which means nothing outside this process — in `fresh` for the same reason `starting` is, since served from `_LAST_STATUS` it would go stale for the 20-30s an unlock holds `_ACTION_LOCK`, most of the way to the page's own threshold. It exists because a frozen MJPEG frame looks perfectly live: the stream simply stops receiving parts, the `<img>` holds its last frame and never fires `onerror`, and on a wedge the endpoint still answers 200 (orientation() times out and the handler falls through to the go-ios branch), so `loadStatus`'s unconditional `screen.classList.remove('dead')` un-dimmed the picture and rewrote the caption to "Live view is on" over a phone answering nothing — the same lying-status bug the 2026-08-14 review fixed for the input flag. The success branch overwrites it with 0.0 rather than trusting the watchdog's clock: `_heal_loop` is the ONLY writer of `down_since` and only on its 20s poll, so `POST /api/up` (the Restart link button, the documented repair after a replug) and `/api/unlock` left `{"link": "up", "silent_for": 300}` in one breath and the page dimmed the freshly restored, moving picture for up to a full `_HEAL_POLL`; corrected in the endpoint so every consumer inherits it, and `down_since` itself is left alone because a handler writing it would be voting in a healing decision it cannot see. viewer.html dims on `streaming && silent_for >= STALL_SECONDS` (60, a UI threshold and a one-line revert: above `_HEAL_MIN_SILENCE` 45 and above every legitimate long hold — unlock ~11s, first gesture after deep sleep 20.5s, read_messages 10-20s — all of which LAND ACTIONS, which `_actions_landing()` reads and which zeroes the clock outright). The `streaming &&` half is not optional: where WDA has never come up `silent_for` grows without bound while `onerror` has already handed the picture to the go-ios `/api/screenshot` poll, which is genuinely live, and dimming that is the same lie pointed the other way. The caption states silence and claims NO recovery (a test pins that "trying to recover" is absent), because `_should_heal` wants lockdown and deep sleep gates lockdown, so nothing is being tried for hours; the wedge's own repair is not lost with it, since btn-up stays visible in every failing state. `loadStatus` holds a `statusInFlight` re-entrancy flag — on a wedge it runs the client's full 10s inside `orientation()` while `setInterval` keeps firing every 5s — and deliberately NOT an `AbortSignal` on `getJSON`: that aborts the browser fetch while the handler keeps running into the wedged WDA, and `getJSON` also carries POST `/api/stop` (a kill switch that landed would report failure) and `/api/doctor` (~2s of subprocesses, slowest during the very outage the checks exist for); a test pins its absence. `loadStatus` and `loadPhone` return early while `document.hidden`: closing `screen.src` alone achieved nothing, because the 5s `loadStatus` re-ran `startStream()` on the very next tick (Chrome coalesces hidden-tab timers to 1s granularity, it does not stop them), so the ~334KB/s saving lasted about 5 seconds. `Handler` serves HTTP/1.1 with `disable_nagle_algorithm`, so the page's `/api/*` calls stop reconnecting (replicated locally with a copy of this handler, 300 requests each: 0.54-0.60ms median against 0.12-0.29ms keep-alive). That needs an accurate Content-Length on EVERY response — `_send` is the only `wfile.write` in the file and always sets one, and anything new that writes the socket directly must too, or the browser hangs waiting for a body that already ended. It also makes an UNREAD request body the next request on the wire, which is a hole straight through the origin guard: a cross-origin page can put a well-formed, Host-correct `POST /api/tap` in the body of a `text/plain` POST, and a 403 answered without reading the body would leave it sitting in the buffer to be served as a real request. So every early return that answers without reading a body sets `close_connection` first — both do_POST guards and do_GET's 403, exactly what HTTP/1.0 did by accident — `_send` emits `Connection: close` when that flag is set so a pooling client does not retry into a dead socket, and a request carrying `Transfer-Encoding` is refused outright, because it has no Content-Length and its body would be left on the wire by definition. A test drives two requests down one real socket, and two more fire the smuggling attempt (plain and chunked) and assert nothing but EOF follows the 403. `Handler.timeout = 60` is the price of that keep-alive: a tab that goes away (closed, slept, crashed) otherwise parks a `ThreadingHTTPServer` thread in `rfile.readline()` with no deadline, one per connection, for the life of the process. It is the SOCKET READ timeout, which `BaseHTTPRequestHandler` turns into `close_connection`, and it does NOT bound handler execution — `/api/unlock` (up to ~45s on its 45s client) and `/api/read-thread` (10-20s) are untouched, proven by a test running a 2s handler under a 1s timeout rather than reasoned about. `socketserver` applies it in `setup()`, at connection open, so a test that shortens it has to do so BEFORE it connects. `loadApproval` stays UNGATED on purpose — it is the send-approval safety gate, and it reads a local JSON file, not the phone.

- Multi-device instances: the harness runs as an INSTANCE — `SIDETAP_UDID` pins every go-ios call through `device.pin_udid()`, the one chokepoint inside `_run`/`_spawn` (capture.py and syslog.py route their raw invocations through it; `list` stays global so the doctor and the fleet roster see every phone, `tunnel` is go-ios's all-devices daemon owned by whichever instance starts it first). `SIDETAP_STATE_DIR` re-homes `.state` and everything keyed off `config.STATE_DIR`; `WDA_PORT`/`MJPEG_PORT` are env-tunable PC-side listen ports (phone side stays 8100/9100 — each phone has its own USB namespace). All defaults are byte-identical to the single-phone harness and a test pins that; per-command `--udid` scoping is UNVERIFIED until a second phone exists. The fleet launcher/roster/dashboard live in the PRIVATE sidetap-pro repo (design docs there); `launch.py --no-browser` exists for it. The viewer's origin guard accepts `Sec-Fetch-Site: same-site` for exactly this reason — the fleet dashboard (:8769) iframes the viewer cross-port, which is same-site not same-origin (403'd live, 2026-09-01, docs/ERRORS.md); loopback-served pages are local software that could hit the unauthenticated API directly, remote pages stay cross-site, and cross-port POSTs still die on the Origin check because fetch() sends Origin and navigations do not.

## Commands

- Run everything: `python launch.py` (viewer opens immediately; `up()` runs in a background thread). Double-click equivalents: `sidetap.cmd`, or the Desktop/Start Menu **SideTap** shortcut (`scripts/install_shortcut.ps1` installs it, `-Startup` adds run-at-boot, icon in `assets/sidetap.ico`)
- Tests: `python -m pytest tests -q`
- Diagnose: `phone-harness doctor` (never guess at connection problems — run this)
- After a replug: the viewer's Restart link button, or `phone-harness up`
- Enable touch input (free Apple ID): `phone-harness fix-input`, then click Start in Sideloadly (mid-week: `phone-harness fix-input .state/profile.mobileprovision` skips Sideloadly; installs need the phone unlocked)
- Never miss the weekly re-sign: `phone-harness notify-expiry --install` (daily toast when <36h left)

## Rules

- Coordinates are points, not pixels. The UI tree and taps use the same units.
- Keep `wda_client.py` free of go-ios knowledge and `device.py` free of HTTP knowledge.
- New agent primitives go in `helpers.py` and must be added to `__all__` (mcp_server.py picks most of them up from its `_TOOLS` list — add there too if MCP-safe).
- No new runtime dependencies beyond `requests` and `mcp` without a stated reason.
- Driving the phone needs the user's hardware set up (docs/setup-windows.md); unit tests must pass without a phone.
