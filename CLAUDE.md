# SideTap

LLM agents drive a real iPhone from Windows over USB + WebDriverAgent (go-ios).
Windows rebuild of ShawnPana/phone-harness (which is macOS-only).

## Architecture

- `src/phone_harness/wda_client.py` — thin HTTP client for WebDriverAgent (:8100). requests only. Each client owns ONE persistent `requests.Session` (`self._http`) so the loopback connection to WDA stays warm: the module-level `requests.request` builds and closes a throwaway Session per call, and every helper funnels through `_request`, so a per-call TCP connect was paid on every tap, read and screenshot. Anything monkeypatching the transport must patch `requests.Session.request`, not `requests.request`. `active_element`/`element_clear`/`element_value`/`find_first` are the ONLY element-id lookups in the codebase: `set_field_text` clears and reads back a field, and `current_page()` reads one attribute off one element. Perception stays on `/source`. A BOUNDED type query is cheap (`**/XCUIElementTypePageIndicator` + value = 0.37s against 3.0-5.7s for a Home Screen `/source`), but an UNBOUNDED one is not merely slow — `**/*` on the Home Screen KILLED WDA outright and took the session with it (2026-08-12, docs/ERRORS.md). `find_first` returns one id and never a list so it cannot quietly become a perception path. Kill switch: a `.state/STOP` file blocks every action POST at the `_request` chokepoint (perception GETs keep working). The same chokepoint appends every successful action POST to `.state/agent_activity.log` (bounded ring; typed text NEVER recorded, only char counts — it can be a passcode). WDA holds exactly ONE session and creating a new one evicts the holder, so every client shares the id published in `.state/wda_session`: adopt it, heal an unusable id by adopting the replacement or minting fresh. "Unusable" covers "invalid session" AND the `point.x != INFINITY` state — a session that crosses a screen lock keeps answering GETs but fails every /actions forever (bit the Unlock button live; a test pins the heal). The session creator applies the post-gesture waits from config (WDA_IDLE_WAIT=2, WDA_ANIM_COOLOFF=0 — the cool-off default of 2 cost 2-5s per swipe under scroll momentum; ~0.7s with it at 0, measured on device).
- `src/phone_harness/trust.py` + `approval.py` — prompt-injection defense. `trust` holds the sticky process taint flag (set by `ui_tree`/`screenshot`/`read_messages`; `trust.internal()` keeps a helper's own bookkeeping reads from counting), the heuristic scanner (flags are a SIGNAL for the human card, never an allow/deny — no filter detects injection reliably), and the data-not-instructions envelope the MCP layer wraps screen reads in. The envelope pays the full 48-word `WARNING` only when the scanner actually flags something; a clean read carries `WARNING_SHORT` instead, because the model already has the same rule in the server instructions and in every read tool's description, and the full text nested once per batched step inside `act()`, which exists to cut cost. Shorter, never silent: the scanner has false negatives, so a clean read still says the content is data. `approval` is the `.state/pending_send.json` handshake that blocks `send_message` until the viewer answers; fail closed, timeout means deny, one card at a time. `approval.mode()` is the always/flagged/off setting, read at SEND TIME (not import) because the human flips it mid-session in a different process: `.state/send_approval` (viewer toggle) beats `SEND_APPROVAL` in `.env`, and anything unrecognized falls back to `always` — a setting that cannot be read must never be the one that disables the gate. `set_mode` is deliberately absent from `_TOOLS`, `_ACT_TOOLS` and `helpers.__all__`, and a test pins that. `send_message` gains NO bypass argument on purpose — every parameter of an MCP tool is reachable by an injected instruction — so the viewer's own `/api/text` uses the thread-local `trust.human_initiated()` instead (it also holds `_ACTION_LOCK`, so gating there would freeze every viewer gesture for the whole timeout). `type_text` refuses PHONE_PASSCODE; `unlock()` drives the client directly and is unaffected. The MCP reading tools must be registered AFTER their `__doc__` is extended: FastMCP reads the docstring at registration, not at call time.
- `src/phone_harness/device.py` — go-ios wrapper; detached tunnel/runwda/forward processes, pids+logs in `.state/`. `ios_path()` falls back to `%APPDATA%\npm\ios.exe` when PATH lookup fails — Windows truncates a >4095-char registry PATH in the logon environment, so shortcut/Startup launches can miss the npm dir (bit the Startup shortcut live; a test pins the fallback). `detect_wda_bundle()` caches its hit in `.state/wda_bundle` because deep sleep EMPTIES `ios apps --list` while the app is still installed (seen live); `lockdown_ready()` (`ios date` exit code) is the "has the human woken the phone" probe — deep sleep gates lockdown (ReadPair errors) while tunnel services keep working. `ddi_mounted()`/`mount_ddi()`: an iOS UPDATE silently unmounts the Developer Disk Image, and without it testmanagerd refuses every test session — runwda dies in dtx channel timeouts that look like a broken tunnel (bit live 2026-08-10); mounting needs the phone UNLOCKED (DeviceLocked otherwise), so `up()` auto-mounts and the doctor names it.
- `src/phone_harness/admin.py` — `doctor` (ordered checks, each names its fix; the STOP kill switch is checked FIRST, then LAN exposure and the 7-day signature countdown), `up` (serialized by `_UP_LOCK`: launch.py's background bring-up and the viewer's Restart link can overlap; `bringing_up()` reports that lock so the viewer can say "starting" instead of "broken"), `down`, `notify-expiry` (Windows toast when <36h remain on the signature; `--install` registers a daily 10:00 scheduled task via phone-harness.cmd — renewal itself always needs one Sideloadly click, Apple auth mints the profile).
- `src/phone_harness/capture.py` — screenshots. Prefers WDA's HTTP `/screenshot` (sessionless client, cannot steal the one WDA session) with a 10s back-off; falls back to the `ios screenshot` subprocess, which is the only path that works before signing.
- `scripts/lock_ports.ps1` — self-elevating firewall rule blocking LAN access to :8100/:9100 (WDA has no auth). Fired by the viewer's Lock ports button or run by hand.
- `src/phone_harness/signing.py` — `fix-input`: builds a p12 from Sideloadly's cert, captures the profile Sideloadly mints (Temp watcher), re-signs WDA incl. the nested `.xctest` via `ios sign app`. All local; no Apple auth.
- `src/phone_harness/helpers.py` — agent API (`tap`, `tap_text`, `ocr`, `open_app`, …). `ocr()` reads the UI tree; the tree is cached ~2s and every action invalidates it (WDA `/elements` queries were measured SLOWER than `/source` on device — don't reintroduce them). `_invalidate_tree()` only fires in the calling PROCESS, so the cache is also keyed on the mtime of `.state/agent_activity.log`, which every process appends to: without that, a human tap in the viewer left the agent serving a stale tree for up to the TTL and tapping the previous screen's coordinates. `wait_stable()` compares its first pair of screenshots IMMEDIATELY — callers arrive straight after a gesture WDA already settled (~0.7s), so sleeping before the first compare cost a guaranteed extra interval up to 9x per `scroll_until_found` and 17x per `find_on_home_screen`; measured 299ms on a still screen after the fix. `set_field_text(field, text)` is the ONLY correct way to put text in a non-empty field: `type_text` is `POST /wda/keys`, which APPENDS at the cursor (confirmed on device: two type_text calls give "AAABBB"), and iOS keeps an unsent draft per Messages thread, so typing straight in sends draft+text. It clears (Clear-text button, else WebDriver `element/clear`, else backspaces), types, then reads the value back — note `collect_texts` prefers `label`, which for a text field is the PLACEHOLDER ("Address", "Message"), so the real content only comes from `element_value`. `send_message` REFUSES to tap Send when the read-back differs from what was approved: the approval card is shown `text` 15 lines before anything is typed, so a surviving draft would put unapproved content on the wire. `unlock()` decides from the screen — NEVER from `/wda/locked`, which can report unlocked with the pad on screen (a test pins this): wake + bottom-edge swipe, type PHONE_PASSCODE only if the pad actually appeared, one attempt only (iOS lockout), success = pad gone. It runs on a patient 45s clone of the given client (the first gesture after a deep sleep blocked WDA 20.5s, measured — a 10s client aborts a swipe that still lands), polls for the pad instead of peeking once, and spends exactly one extra wake+swipe when the first burned on a re-slept screen. `send_message()`/`read_messages()` find the thread by TYPING the name into Messages search and tapping the Conversations result cell (bare name, no preview chrome) — never by scrolling the list, whose row taps missed mid-settle and whose top-left "back" geometry is also the list's profile button (both bit live 2026-08-10; `_go_back` now requires a compose bar on screen before tapping). The opened thread's header must still match the contact before anything is typed. `current_page()` reads the `PageIndicator`'s `value` (`"Page 4 of 8"`) for exact Home Screen position: index 0 is Today View, 1..total are real pages, total+1 is the App Library — iOS numbers all three itself. It goes through `find_first`, NOT `ui_tree()`: the Home Screen is the worst case for `/source` (554-610 nodes, 244 KB, 3.0-5.7s measured, against 0.22s inside Calculator), and one targeted lookup is 0.37s. `ocr()` CANNOT see the element either way, because `collect_texts` prefers `label`, which is null on it, so it falls back to `name` ("Page control") and drops `value`. `goto_home_page(n)` walks there and re-reads to confirm, raising rather than leaving you short; it sleeps NOWHERE — WDA already waits for idle inside the `/actions` call, so the old 0.55s `_PAGE_SETTLE` after each swipe counted the same wait twice (the first read after `swipe()` returns is correct 6/6; a six-page walk went 10.7s -> 7.0s, and a two-page walk 10.75s -> ~2.5s). `press_home()` still cannot reach a page at all — `/wda/homescreen` only exits an app to the springboard, and from page 4 two consecutive calls both stayed on page 4 (from the App Library it does not even leave) — but it now WAITS for the springboard to actually arrive: `/wda/homescreen` is not reliably synchronous (it returned in ~50ms with the app still frontmost on two tries of three, the springboard landing ~830ms later), and returning early made the viewer's second Home press read a stale `active_app` and press home again instead of walking. It is bounded and never raises, because the physical gesture cannot fail either. `find_on_home_screen()` starts with `goto_home_page(1)`: it used to press home TWICE believing the second press paged back, so the scan silently began wherever the phone already was and could never see the pages behind it (from page 2 it scanned page 2 first, caught on device 2026-08-12).
- `src/phone_harness/run.py` — CLI; no-arg mode executes stdin with helpers in scope; autoloads `agent-workspace/agent_helpers.py`; `mcp` subcommand starts the MCP server.
- `src/phone_harness/mcp_server.py` — helpers as native typed MCP tools (`claude mcp add sidetap -- phone-harness mcp`). Registers the helpers functions directly so schemas track their real signatures; `screenshot`/`unlock` get wrappers (bytes return / internal client param), and `act` batches several tool calls into one round trip (whitelisted via `_ACT_TOOLS`; screenshot excluded — bytes don't nest in JSON). `compact()` now LIVES IN `helpers` (and in `__all__`), so a CLI-piped script gets the same shrink the MCP tools get; `mcp_server` imports it as `_compact`. It also caps the row count (default 60) and appends an explicit "[N more rows not shown]" marker rather than truncating silently. It shrinks what `ocr`/`find_text` hand the model by 64% (measured, four real screens): `_NOISE_TYPES` wrappers go, `rect` goes (x/y is what a tap needs), a label repeating the text of the control enclosing it goes — which also stops the classic mis-tap on the inner `StaticText` — and identical text overlapping itself collapses via `_rank` (actionable type, then larger). Only `_LABEL_TYPES` (`StaticText`, `Image`) are ever droppable; a `Switch` inside its row and a `checkmark` reporting selection are independently tappable/stateful and MUST survive (tests pin both). `_NOISE_TYPES` is `Application`/`Window` ONLY — `Other` was in it briefly and that silently ate the Home Screen search affordance, which is an `Other`; don't put it back. `ocr(full=True)` opts out. This lives at the MCP boundary, NOT in helpers — `viewer.py`, `send_message` and the tests need the full tree, same reasoning as the untrusted-content envelope. Needs the `mcp` package (the one dependency beyond requests).
- `skills/` — agent skills shipped WITH the product (`phone`, `phone-gotchas`), for users to copy into `~/.claude/skills/`. These are the public, genericized copies: no machine-specific paths, no personal device details. Claude Code only ever loads the copies under `~/.claude/skills/`, never these, so a change to a trap or a helper must land in BOTH places — edit here first, then re-copy. Keep this copy free of anything specific to one machine or one phone.
- `site/` — sidetap.io marketing site, fully self-contained (Vercel project `sidetap` has rootDirectory=site so the Python repo root never confuses its build detection). Static single page wearing the brand tokens from `C:/Projects/animations/brands/phoneclaude.json` (blue = action only, red = STOP only, green = passing checks only); its signature element is a working on-page kill switch. Deploys via Vercel git integration on every push to main; `site/api/waitlist.js` emails Pro-waitlist signups to wes@practicalsystems.io through Resend (`RESEND_API_KEY` lives on the Vercel project, not in local `.env`). Design decisions: `docs/superpowers/specs/2026-08-10-sidetap-website-design.md`.
- `src/phone_harness/viewer.py` + `viewer.html` — human surface: live MJPEG screen (:9100), click-to-tap, drag-to-swipe, keyboard typing, paste box for long text, Notifs/Control edge-gesture buttons, zero-scroll dashboard above 1100px (NOTHING in the document scrolls; wheel over the phone drives the phone — the `wheel` listener is `{passive:false}` and `preventDefault`s, so that holds at every width). BELOW 1100px the dashboard stacks to one column and the document scrolls: the three columns cannot hold their content beside the fixed phone pane, and a centred non-wrapping row clipped BOTH edges, which can reach the phone pane and STOP. Clipping the kill switch is worse than scrolling: one-line header (N check dots + count + battery/lock/app glance), permanent columns Actions (text someone / open app, learned+pinned chips), Agent (Activity + Recent sends, hard-capped rows), Phone (passive info), Debug (ast-whitelisted one-liners via /api/console — no eval; entries clamp to 6em; collapsed by default behind a "Debug ▸" toggle with a what-is-this blurb, expand state in localStorage — it exists to run the agent's own helpers when one misbehaves, not for normal control); details live in a single overlay shell (checks, fix-input wizard, full feeds — Escape closes, keydown guard keeps overlay keys off the phone). Overflow policy: hard count caps + degrade-to-fit on render (text-height varies, so count caps alone clipped cards in the adversarial pass — never reintroduce bare caps); checks auto-open the overlay only on an ok→fail transition, once per page load, Unlock/Lock and Restart link buttons, red STOP/RESUME kill switch, red LAN-exposure banner (loud by default; probed in the background) (:8770, VIEWER_PORT to override; 8765 belongs to the Practical Systems API). All `/api/*` calls are origin-guarded against cross-site/DNS-rebinding. Deep sleep kills WDA (~15min after the screen darkens) and NOTHING over USB can wake the phone, so a watchdog thread self-heals: it polls `device.lockdown_ready()` and reruns `up()` the moment the human wakes the phone (cool-down guarded; `/api/unlock` names this exact move when the link is down instead of timing out). Gestures serialize through `_ACTION_LOCK`, but a gesture that cannot take it within `_ACTION_WAIT` (2s) is DROPPED with a 409, never queued: the lock is held 11s by an unlock from a fresh lock and 20-30s after a deep sleep, and a gesture that waits that long is no longer aimed at the screen the human saw. Measured 2026-08-11 before the fix: four taps made during one 11s unlock all executed AFTER it finished, 4.8-9.5s stale, landing on the unlocked home screen — that burst is what "runaway" looked like. The other half of the fix is the `busy` label on the phone pane (`withBusy`), because an unlabelled 20s freeze is what makes someone click again in the first place; clicks during it are answered locally and never sent. `/api/unlock` passes the viewer's own client into `helpers.unlock(c)` (unlock is timing-sensitive; no session re-discovery mid-wake). The viewer retunes the MJPEG stream whenever the session id changes; gesture waits ride with the shared session (see wda_client.py). A stationary hold is a LONG PRESS, not a tap: it fires on a local `LONG_PRESS_MS` (400ms) timer while the button is still down, so the phone's context menu opens during the hold instead of a second after release, and a filling ring is the only signal it registered (the device press itself takes `LONG_PRESS_SECONDS`, 0.8s, so the menu trails the ring). Moving past the same 8px that separates a tap from a swipe cancels it; once fired, `pointerup` sends nothing more. The Home button does what the PHYSICAL Home gesture does, and which of its two jobs it runs depends on what is frontmost (`_app_is_open`, one `active_app()` read; unknown falls back to the walk so it can never become a dead button): from an app it only leaves the app (`press_home()`, 0.77-1.49s end to end), and only a second press, with springboard already frontmost, walks to page 1 (`helpers.goto_home_page(1)`, ~2.5s from page 3, down from 10.75s). Both halves depend on `press_home()` waiting for the springboard: while it could return early, press 1 answered in 0.11s and press 2 then read a stale `active_app`, pressed home a second time and left the phone on page 3 (measured 2026-08-12, before that fix). Walking unconditionally was the first shape and it froze the phone for seconds behind a busy label just to minimise an app, which is most of what the button gets used for. It runs behind a `withBusy` label and must NOT be routed through `gesturePost`: that opens with a `phoneBusy()` guard, so nesting it inside `withBusy` makes the button set its own label, refuse it, and silently send nothing (shipped exactly once, 2026-08-12; a test now scans `viewer.html` for the nesting). The checks RE-RUN THEMSELVES while any of them fails (3s, 3s, 5s, 8s, 15s, then every 30s) and stop once green: `launch.py` opens the browser immediately and brings the link up in a background thread, so the first run always lands mid bring-up, and running once at page load froze that red result until someone clicked Refresh — which is exactly what "the checks are always yellow until I refresh" was. It must also STOP once green: a full run is ~2s of go-ios subprocesses plus a screenshot (measured), so `/api/doctor` also serves its last result while `_ACTION_LOCK` is held, same reasoning as `/api/status` and `/api/phone`. While `admin.bringing_up()` is true the header reads "Starting link…" with grey `wait` dots instead of a red count, and the overlay does NOT auto-open — that now takes TWO consecutive failing runs with no bring-up in flight, because one is how every boot legitimately starts. `_kill_stale_viewer()` kills the old viewer WITHOUT `/T`: the tunnel and the forwards are CHILDREN of the launch.py that started them, so a tree kill there takes the phone link down as a side effect of restarting the UI, and `up()` is already past its "Already up" early return by then (measured 2026-08-12: 11 green checks, then a second launch left tunnel and WDA dead; `down()` is what stops those, by their own pid files).

## Commands

- Run everything: `python launch.py` (viewer opens immediately; `up()` runs in a background thread). Double-click equivalents: `sidetap.cmd`, or the Desktop/Start Menu **SideTap** shortcut (`scripts/install_shortcut.ps1` installs it, `-Startup` adds run-at-boot, icon in `assets/sidetap.ico`)
- Tests: `python -m pytest tests -q`
- Diagnose: `phone-harness doctor` (never guess at connection problems — run this)
- After a replug: the viewer's Restart link button, or `phone-harness up`
- Enable touch input (free Apple ID): `phone-harness fix-input`, then click Start in Sideloadly (mid-week: `phone-harness fix-input .state/profile.mobileprovision` skips Sideloadly; installs need the phone unlocked)
- Never miss the weekly re-sign: `phone-harness notify-expiry --install` (daily toast when <36h left)

## Rules

- Coordinates are points, not pixels. The UI tree and taps use the same units.
- Keep `wda_client.py` free of go-ios knowledge and `device.py` free of HTTP knowledge.
- New agent primitives go in `helpers.py` and must be added to `__all__` (mcp_server.py picks most of them up from its `_TOOLS` list — add there too if MCP-safe).
- No new runtime dependencies beyond `requests` and `mcp` without a stated reason.
- Driving the phone needs the user's hardware set up (docs/setup-windows.md); unit tests must pass without a phone.
