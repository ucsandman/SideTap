# SideTap

LLM agents drive a real iPhone from Windows over USB + WebDriverAgent (go-ios).
Windows rebuild of ShawnPana/phone-harness (which is macOS-only).

## Architecture

- `src/phone_harness/wda_client.py` — thin HTTP client for WebDriverAgent (:8100). requests only. Each client owns ONE persistent `requests.Session` (`self._http`) so the loopback connection to WDA stays warm: the module-level `requests.request` builds and closes a throwaway Session per call, and every helper funnels through `_request`, so a per-call TCP connect was paid on every tap, read and screenshot. Anything monkeypatching the transport must patch `requests.Session.request`, not `requests.request`. `find_first`/`element_clear`/`element_value` are the ONLY element-id lookups in the codebase: `set_field_text` clears and reads back a field, and `current_page()` reads one attribute off one element. There is deliberately NO `active_element()` and adding one back is a bug: `GET /element/active` answers a Messages thread with a message BUBBLE (`XCUIElementTypeTextView` named `CKBalloonTextView`) while the caret is blinking in the compose bar, so the field clear ran on a message — which is a LONG PRESS, and that is what popped the Tapback picker open mid-send — and the read-back returned the message's text, so `send_message` refused what it had correctly typed (2026-08-12, docs/ERRORS.md). Resolve the field you mean with a bounded class chain instead (`helpers._field_element`). Perception stays on `/source`. A BOUNDED type query is cheap (`**/XCUIElementTypePageIndicator` + value = 0.37s against 3.0-5.7s for a Home Screen `/source`), but an UNBOUNDED one is not merely slow — `**/*` on the Home Screen KILLED WDA outright and took the session with it (2026-08-12, docs/ERRORS.md). `find_first` returns one id and never a list so it cannot quietly become a perception path. Kill switch: a `.state/STOP` file blocks every action POST at the `_request` chokepoint (perception GETs keep working). The same chokepoint appends every successful action POST to `.state/agent_activity.log` (bounded ring; typed text NEVER recorded, only char counts — it can be a passcode). WDA holds exactly ONE session and creating a new one evicts the holder, so every client shares the id published in `.state/wda_session`: adopt it, heal an unusable id by adopting the replacement or minting fresh. "Unusable" covers "invalid session" AND the `point.x != INFINITY` state — a session that crosses a screen lock keeps answering GETs but fails every /actions forever (bit the Unlock button live; a test pins the heal). The session creator applies the post-gesture waits from config (WDA_IDLE_WAIT=2, WDA_ANIM_COOLOFF=0 — the cool-off default of 2 cost 2-5s per swipe under scroll momentum; ~0.7s with it at 0, measured on device). `orientation()` is the cheap guard for anything memoising `window_size()`: 7.7ms against 201ms (measured 2026-08-14). The gap is NOT session overhead — session routing is FREE (`GET /session/{id}` is 4.2ms and `/session/{id}/orientation` 7.7ms) — it is that `/window/size` resolves the ACTIVE APPLICATION's frame and orientation does not; `wda/activeAppInfo` (102ms) and `wda/screen` (295ms) pay the same tax. So the rule is avoid calls that RESOLVE THE ACTIVE APP, never "avoid session-scoped calls" — that theory was measured dead. Being a `_session_request` is load-bearing twice over: it heals an evicted session like any other call, and it raises `WDAError` when WDA is gone, so a caller serving a memo can still tell a live link from a dead one.
- `src/phone_harness/trust.py` + `approval.py` — prompt-injection defense. `trust` holds the sticky process taint flag (set by `ui_tree`/`screenshot`/`read_messages`; `trust.internal()` keeps a helper's own bookkeeping reads from counting), the heuristic scanner (flags are a SIGNAL for the human card, never an allow/deny — no filter detects injection reliably), and the data-not-instructions envelope the MCP layer wraps screen reads in. The envelope pays the full 48-word `WARNING` only when the scanner actually flags something; a clean read carries `WARNING_SHORT` instead, because the model already has the same rule in the server instructions and in every read tool's description, and the full text nested once per batched step inside `act()`, which exists to cut cost. Shorter, never silent: the scanner has false negatives, so a clean read still says the content is data. `approval` is the `.state/pending_send.json` handshake that blocks `send_message` until the viewer answers; fail closed, timeout means deny, one card at a time. `approval.mode()` is the always/flagged/off setting, read at SEND TIME (not import) because the human flips it mid-session in a different process: `.state/send_approval` (viewer toggle) beats `SEND_APPROVAL` in `.env`, and anything unrecognized falls back to `always` — a setting that cannot be read must never be the one that disables the gate. `set_mode` is deliberately absent from `_TOOLS`, `_ACT_TOOLS` and `helpers.__all__`, and a test pins that. `send_message` gains NO bypass argument on purpose — every parameter of an MCP tool is reachable by an injected instruction — so the viewer's own `/api/text` uses the thread-local `trust.human_initiated()` instead (it also holds `_ACTION_LOCK`, so gating there would freeze every viewer gesture for the whole timeout). `type_text` refuses PHONE_PASSCODE; `unlock()` drives the client directly and is unaffected. The MCP reading tools must be registered AFTER their `__doc__` is extended: FastMCP reads the docstring at registration, not at call time.
- `src/phone_harness/device.py` — go-ios wrapper; detached tunnel/runwda/forward processes, pids+logs in `.state/`. `ios_path()` falls back to `%APPDATA%\npm\ios.exe` when PATH lookup fails — Windows truncates a >4095-char registry PATH in the logon environment, so shortcut/Startup launches can miss the npm dir (bit the Startup shortcut live; a test pins the fallback) — and then to `%LOCALAPPDATA%\SideTap\bin\ios.exe`, where `site/install.ps1` puts go-ios on machines that never had Node/npm (a test pins this one too). `detect_wda_bundle()` caches its hit in `.state/wda_bundle` because deep sleep EMPTIES `ios apps --list` while the app is still installed (seen live); `lockdown_ready()` (`ios date` exit code) is the "has the human woken the phone" probe — deep sleep gates lockdown (ReadPair errors) while tunnel services keep working. `ddi_mounted()`/`mount_ddi()`: an iOS UPDATE silently unmounts the Developer Disk Image, and without it testmanagerd refuses every test session — runwda dies in dtx channel timeouts that look like a broken tunnel (bit live 2026-08-10); mounting needs the phone UNLOCKED (DeviceLocked otherwise), so `up()` auto-mounts and the doctor names it. `list_apps()` persists a non-empty result to `.state/apps_cache.json` and falls back to it when the live `ios apps --list` comes back EMPTY — the same deep-sleep failure mode `detect_wda_bundle` already caches around; a live non-empty result always overwrites it, so a newly installed app stays findable. It lives INSIDE `list_apps()`, so `helpers.open_app` and admin both inherit it with zero changes, and it fixes the live bug where `open_app` raised "Unknown app" for an installed app after deep sleep. `memoized_run()` scopes `list_devices()`/`list_apps()`/`_netstat_ano_lines()` to ONE caller-defined block (one ~4s doctor pass) so the same 207ms spawn is not paid twice — backed by `threading.local()`, NEVER a module global: `viewer.py` runs a `ThreadingHTTPServer` plus `_heal_loop` and `_refresh_lan_state`, and with a shared global two overlapping blocks stomp each other's restore and leave a non-None dict frozen for the life of the process after both have exited (a frozen empty `list_devices()` makes `up()` and the viewer's Restart button report "No iPhone found" forever while the doctor panel shows the phone connected). Nothing survives the block, because a stale check is a lying check. Two independent adversarial reviews caught it 2026-08-14; a test pins the thread isolation.
- `src/phone_harness/admin.py` — `doctor` (ordered checks, each names its fix; the STOP kill switch is checked FIRST, then LAN exposure and the 7-day signature countdown), `up` (serialized by `_UP_LOCK`: launch.py's background bring-up and the viewer's Restart link can overlap; `bringing_up()` reports that lock so the viewer can say "starting" instead of "broken"), `down`, `notify-expiry` (Windows toast when <36h remain on the signature; `--install` registers a daily 10:00 scheduled task via phone-harness.cmd — renewal itself always needs one Sideloadly click, Apple auth mints the profile). `doctor_results()` wraps its CHECKS loop in `device.memoized_run()`, so `ios list`, `ios apps --list` and netstat each spawn once per pass instead of twice (~500-700ms at the measured 207ms spawn floor, and the viewer re-runs doctor ~6 times in the first minute of every boot); the memo dies with the pass, so a second run never reports stale state. `_up()`'s WDA poll is `_wait_for_wda(client, deadline, interval=0.25)`: `is_up()` is a 3.8ms `/status` probe, so the old 2s sleep wasted up to 2s per iteration on every launch, Restart-link click and deep-sleep self-heal; deadline and give-up behaviour are unchanged, and the progress dot is throttled so the faster interval does not flood the log. `_check_signature` PASSES during the countdown and fails ONLY once the signature has actually expired. Input works the whole 7 days, and by the note above nothing can renew it early, so failing at <48h left reddened the header, counted as "1 check failing", auto-opened the overlay and raised the amber banner (viewer.html keys it off `!sig.ok`) for two days over a working system — while its own fix line read "No click can extend it early". A check that fails while the thing works is the same lying-status bug as a green over a dead link, pointed the other way. The countdown stays visible in the viewer's Phone pane, which renders that detail whatever `ok` is, and `notify-expiry` still toasts under 36h.
- `src/phone_harness/capture.py` — screenshots. Prefers WDA's HTTP `/screenshot` (sessionless client, cannot steal the one WDA session) with a 10s back-off; falls back to the `ios screenshot` subprocess, which is the only path that works before signing.
- `scripts/lock_ports.ps1` — self-elevating firewall rule blocking LAN access to :8100/:9100 (WDA has no auth). Fired by the viewer's Lock ports button or run by hand.
- `src/phone_harness/signing.py` — `fix-input`: builds a p12 from Sideloadly's cert, captures the profile Sideloadly mints (Temp watcher), re-signs WDA incl. the nested `.xctest` via `ios sign app`. All local; no Apple auth. The captured/supplied profile lands in a `.pending` staging file and is committed to `.state/profile.mobileprovision` only AFTER `ios sign app` succeeds — the doctor's countdown reads that file as "what is on the phone", so committing first turned a failed re-sign into a fresh 7-day PASS over the old dying signature (adversarial review 2026-08-13). Same review: `fix_input` catches `subprocess.TimeoutExpired` (openssl 30s, sign 300s) and returns ok:False instead of letting it kill the viewer's worker thread, and `_capture_via_watcher` deletes a stale `captured.mobileprovision` from Python, loudly — the PS script's own delete runs under SilentlyContinue, and a leftover file is otherwise accepted as this run's mint. Renewal truth (proven 2026-08-14, account-appids.json NearestTtl unchanged by a fresh sign): NOTHING moves the expiry mid-week — Apple pins every re-sign, Sideloadly included, to the App ID's original 7-day window. The countdown resets only with the first sign AFTER expiry, so the countdown check and the toast deliberately do NOT prescribe fix-input until it has expired (a mid-week Sideloadly Start is worse than useless: its bare install breaks WDA with error 103 until a local re-sign, which bit twice on 2026-08-14). Capture windows default to 600s — 180s lost a race to the human+Sideloadly loop.
- `src/phone_harness/helpers.py` — agent API (`tap`, `tap_text`, `ocr`, `open_app`, …). `ocr()` reads the UI tree; the tree is cached ~2s and every action invalidates it (WDA `/elements` queries were measured SLOWER than `/source` on device — don't reintroduce them). `_invalidate_tree()` only fires in the calling PROCESS, so the cache is also keyed on the mtime of `.state/agent_activity.log`, which every process appends to: without that, a human tap in the viewer left the agent serving a stale tree for up to the TTL and tapping the previous screen's coordinates. `wait_stable()` compares its first pair of screenshots IMMEDIATELY — callers arrive straight after a gesture WDA already settled (~0.7s), so sleeping before the first compare cost a guaranteed extra interval up to 9x per `scroll_until_found` and 17x per `find_on_home_screen`; measured 299ms on a still screen after the fix. `set_field_text(field, text)` is the ONLY correct way to put text in a non-empty field: `type_text` is `POST /wda/keys`, which APPENDS at the cursor (confirmed on device: two type_text calls give "AAABBB"), and iOS keeps an unsent draft per Messages thread, so typing straight in sends draft+text. It clears (Clear-text button, else WebDriver `element/clear`, else backspaces), types, then reads the value back — note `collect_texts` prefers `label`, which for a text field is the PLACEHOLDER ("Address", "Message"), so the real content only comes from `element_value`, and an EMPTY field reports its placeholder there too ("iMessage" on the compose bar), so an emptied field never reads back as "". The clear and the read-back both address the field the CALLER named, resolved by `_field_element()` to a class chain (label predicate first, bare type as fallback) AFTER the tap, because the keyboard slide-up moves the compose bar from y=908 to y=601 and the tapped coordinates stop describing it. `send_message` REFUSES to tap Send when the read-back differs from what was approved: the approval card is shown `text` 15 lines before anything is typed, so a surviving draft would put unapproved content on the wire. `unlock()` decides from the screen — NEVER from `/wda/locked`, which can report unlocked with the pad on screen (a test pins this): wake + bottom-edge swipe, and only if the pad actually appeared, enter PHONE_PASSCODE by TAPPING the pad's digit buttons (`_enter_passcode`) — NOT `/wda/keys`, which goes to the FOCUSED element: a lock-screen priority notification held focus while the pad sat behind it and ate all six typed digits (live 2026-08-13, docs/ERRORS.md); typing survives only as the alphanumeric-passcode fallback, and the digit taps run inside `wda_client.redact_actions` because a pad tap's coordinates spell out the passcode and the activity feed never records typed text; the tap burst runs at `waitForIdleTimeout` 0 (`set_wait_for_idle`, restored to WDA_IDLE_WAIT in a finally — the setting rides the SHARED session) because the pad is static and each tap otherwise paid the idle wait plus a sleep, 4.94s for six digits against 2.6-3.1s now (live 2026-08-14) — and the burst must stay ONE REQUEST PER TAP: six down/up cycles batched in one pointer source enter deterministically WRONG digits and six parallel pointer sources KILL WDA outright (both proven in Calculator 2026-08-14, docs/ERRORS.md; on the pad they would be wrong attempts toward an iOS lockout) — one attempt only (iOS lockout), success = pad gone — and "pad gone" is a bounded `find_first` probe for one of the pad's own digits (`_pad_digit_probe`, 0.11s measured), NOT a `/source`: the old sleep(0.7) + full tree read ran against the freshly unlocked Home Screen, `/source`'s worst case, and held the viewer's busy overlay ~5s over a phone that was visibly unlocked (live 2026-08-14; post-tap tail now 0.23s measured, a test pins the single `/source`). It runs on a patient 45s clone of the given client (the first gesture after a deep sleep blocked WDA 20.5s, measured — a 10s client aborts a swipe that still lands), polls for the pad instead of peeking once, and spends exactly one extra wake+swipe when the first burned on a re-slept screen. Past the in-use early return it MINTS a fresh session (`WDAClient.fresh_session()`) before any gesture: a session that crossed a screen lock keeps answering GETs but its first `/actions` hangs ~16s inside XCTest's snapshot timeout before failing `point.x != INFINITY` (16.23s measured 2026-08-14, against a 0.02s fresh create on the same lit lock screen), long enough for the woken screen to re-sleep and burn the swipe — that hang, not the notification itself, was the whole "unlock takes 30s with a priority notification" complaint (the notification just keeps the poisoned session alive-and-lit so the slow path fires every time; docs/ERRORS.md). The pad poll is wall-clock capped at its budget (minimum two reads): it counts attempts assuming a 0.4s `/source`, but a lock-screen `/source` runs ~3s, and 7 polls of a screen a burned swipe never changed cost 21s of the same incident. Its "is the phone genuinely in use" guard treats ONLY the "insert nil object" `WDAError` from `active_app()` as nothing-frontmost and carries on: `GET /wda/activeAppInfo` CRASHES ("attempt to insert nil object") the whole time the lock screen is LIT and recovers when it darkens (reproduced on device 2026-08-13) — a priority notification keeps the lock screen lit for as long as it shows, so every Unlock press during one died on that first call with zero gestures logged, hours after the pad-tapping fix shipped for the same symptom (docs/ERRORS.md has both entries). Any OTHER `WDAError` there re-raises: the phone's state is unknown, and carrying on would Home-press someone out of their app (adversarial review 2026-08-13; the same review made the two-dark-swipes give-up RAISE instead of returning — a silent return had the viewer answering ok:true and the MCP tool saying "unlocked" over a still-dark phone; the attempt count stays bounded at two). `send_message()`/`read_messages()` find the thread by TYPING the name into Messages search and tapping the Conversations result cell (bare name, no preview chrome) — never by scrolling the list, whose row taps missed mid-settle and whose top-left "back" geometry is also the list's profile button (both bit live 2026-08-10; `_go_back` now requires a compose bar on screen before tapping). The opened thread's header must still match the contact before anything is typed. `current_page()` reads the `PageIndicator`'s `value` (`"Page 4 of 8"`) for exact Home Screen position: index 0 is Today View, 1..total are real pages, total+1 is the App Library — iOS numbers all three itself. It goes through `find_first`, NOT `ui_tree()`: the Home Screen is the worst case for `/source` (554-610 nodes, 244 KB, 3.0-5.7s measured, against 0.22s inside Calculator), and one targeted lookup is 0.37s. `ocr()` CANNOT see the element either way, because `collect_texts` prefers `label`, which is null on it, so it falls back to `name` ("Page control") and drops `value`. `goto_home_page(n)` walks there and re-reads to confirm, raising rather than leaving you short; it sleeps NOWHERE — WDA already waits for idle inside the `/actions` call, so the old 0.55s `_PAGE_SETTLE` after each swipe counted the same wait twice (the first read after `swipe()` returns is correct 6/6; a six-page walk went 10.7s -> 7.0s, and a two-page walk 10.75s -> ~2.5s). `press_home()` still cannot reach a page at all — `/wda/homescreen` only exits an app to the springboard, and from page 4 two consecutive calls both stayed on page 4 (from the App Library it does not even leave) — but it now WAITS for the springboard to actually arrive: `/wda/homescreen` is not reliably synchronous (it returned in ~50ms with the app still frontmost on two tries of three, the springboard landing ~830ms later), and returning early made the viewer's second Home press read a stale `active_app` and press home again instead of walking. It is bounded and never raises, because the physical gesture cannot fail either. `find_on_home_screen()` starts with `goto_home_page(1)`: it used to press home TWICE believing the second press paged back, so the scan silently began wherever the phone already was and could never see the pages behind it (from page 2 it scanned page 2 first, caught on device 2026-08-12). `_window_size()` memoises `window_size()` (201ms — WDA answers it from the ACTIVE APPLICATION's frame) keyed on session id AND `orientation()` (7.7ms). The memo is HERE and not in `WDAClient` because ~13 tests use `window_size()` as their one-request session-heal probe. The orientation half is NOT optional: width and height SWAP on rotation, the session id cannot see that, and the memo outlives the whole MCP session — a stale landscape 844x390 makes `unlock()` swipe from x=422 on a 390-point-wide portrait lock screen, so the bottom-edge swipe never lands and the pad never appears, which is the "Unlock did nothing" symptom already in ERRORS.md three times. Read the session id AFTER `orientation()`, never before: orientation is a session request so it heals an evicted session, and a sid sampled first is still the dead one the stale entry is keyed on, so the guard would match itself and serve the stale size. `unlock()` deliberately calls `c.window_size()` DIRECT rather than the memo — it reads once, a lock almost always evicts the session so the memo would miss anyway, and the guard would only add a SECOND round trip to the path where the first gesture after a deep sleep blocked WDA 20.5s. `_clear_field` hunts the Clear-text button ONLY when the caller passes a `SearchField`: that button is a SearchField affordance and the Messages compose bar never grows one, so on `send_message`'s TextField the `ocr()` was a full `/source` (3.5-7.4s, and ALWAYS cold because the tap that just happened invalidated the cache) that could structurally never find anything. `find_on_home_screen` no longer calls `wait_stable()` between pages — WDA_IDLE_WAIT already absorbs the swipe settle inside `/actions` (the same evidence that retired `_PAGE_SETTLE`) and the next `find_text()` re-reads to confirm what landed; 299ms/page. Do NOT extend that removal to `scroll_until_found`, where WDA_ANIM_COOLOFF=0 means nothing else waits list momentum out.
- `src/phone_harness/run.py` — CLI; no-arg mode executes stdin with helpers in scope; autoloads `agent-workspace/agent_helpers.py`; `mcp` subcommand starts the MCP server.
- `src/phone_harness/mcp_server.py` — helpers as native typed MCP tools (`claude mcp add sidetap -- phone-harness mcp`). Registers the helpers functions directly so schemas track their real signatures; `screenshot`/`unlock` get wrappers (bytes return / internal client param), and `act` batches several tool calls into one round trip (whitelisted via `_ACT_TOOLS`; screenshot excluded — bytes don't nest in JSON). `compact()` now LIVES IN `helpers` (and in `__all__`), so a CLI-piped script gets the same shrink the MCP tools get; `mcp_server` imports it as `_compact`. It also caps the row count (default 60) and appends an explicit "[N more rows not shown]" marker rather than truncating silently. It shrinks what `ocr`/`find_text` hand the model by 64% (measured, four real screens): `_NOISE_TYPES` wrappers go, `rect` goes (x/y is what a tap needs), a label repeating the text of the control enclosing it goes — which also stops the classic mis-tap on the inner `StaticText` — and identical text overlapping itself collapses via `_rank` (actionable type, then larger). Only `_LABEL_TYPES` (`StaticText`, `Image`) are ever droppable; a `Switch` inside its row and a `checkmark` reporting selection are independently tappable/stateful and MUST survive (tests pin both). `_NOISE_TYPES` is `Application`/`Window` ONLY — `Other` was in it briefly and that silently ate the Home Screen search affordance, which is an `Other`; don't put it back. `ocr(full=True)` opts out. This lives at the MCP boundary, NOT in helpers — `viewer.py`, `send_message` and the tests need the full tree, same reasoning as the untrusted-content envelope. Needs the `mcp` package (the one dependency beyond requests).
- `skills/` — agent skills shipped WITH the product (`phone`, `phone-gotchas`), for users to copy into `~/.claude/skills/`. These are the public, genericized copies: no machine-specific paths, no personal device details. Claude Code only ever loads the copies under `~/.claude/skills/`, never these, so a change to a trap or a helper must land in BOTH places — edit here first, then re-copy. Keep this copy free of anything specific to one machine or one phone.
- `site/` — sidetap.io marketing site, fully self-contained (Vercel project `sidetap` has rootDirectory=site so the Python repo root never confuses its build detection). Static single page wearing the brand tokens from `C:/Projects/animations/brands/phoneclaude.json` (blue = action only, red = STOP only, green = passing checks only); its signature element is a working on-page kill switch. `site/install.ps1` is served at sidetap.io/install.ps1: the one-line PC-side installer (Python via winget if missing — only trusting an exe that answers `--version`, never the Store stub — repo zip so no git, pip, go-ios pulled straight from its GitHub releases into `%LOCALAPPDATA%\SideTap\bin` so Node stops being a prerequisite, Apple Devices driver app, Desktop shortcut; re-runs are updates and carry `.env`/`.state`/`wda/` across). Deploys via Vercel git integration on every push to main; `site/api/waitlist.js` emails Pro-waitlist signups to wes@practicalsystems.io through Resend (`RESEND_API_KEY` lives on the Vercel project, not in local `.env`). Design decisions: `docs/superpowers/specs/2026-08-10-sidetap-website-design.md`.
- `src/phone_harness/viewer.py` + `viewer.html` — human surface: live MJPEG screen (:9100), click-to-tap, drag-to-swipe, keyboard typing, paste box for long text (Enter in EITHER box sends it — they are "type it, send it" fields; Shift+Enter keeps the browser's own newline and Ctrl+Enter is typed in by hand, because Chromium inserts NOTHING for it in a textarea, measured headless. ANY modifier takes the newline path, so no combo can fire a send by surprise, and Enter respects the disabled button so it cannot double-send one already in flight), Notifs/Control edge-gesture buttons, zero-scroll dashboard above 1100px (NOTHING in the document scrolls; wheel over the phone drives the phone — the `wheel` listener is `{passive:false}` and `preventDefault`s, so that holds at every width). BELOW 1100px the dashboard stacks to one column and the document scrolls: the three columns cannot hold their content beside the fixed phone pane, and a centred non-wrapping row clipped BOTH edges, which can reach the phone pane and STOP. Clipping the kill switch is worse than scrolling: one-line header (N check dots + count + battery/lock/app glance), permanent columns Actions (text someone / open app / go to page / gestures / thread, learned+pinned chips), Agent (Activity + Recent sends, hard-capped rows), Phone (passive info), Debug (ast-whitelisted one-liners via /api/console — no eval; entries clamp to 6em; collapsed by default behind a "Debug ▸" toggle with a what-is-this blurb, expand state in localStorage — it exists to run the agent's own helpers when one misbehaves, not for normal control); details live in a single overlay shell (checks, fix-input wizard, full feeds — Escape closes, keydown guard keeps overlay keys off the phone). Overflow policy: hard count caps + degrade-to-fit on render (text-height varies, so count caps alone clipped cards in the adversarial pass — never reintroduce bare caps) — that policy is why `.chips` carries NO `max-height` in CSS: a fixed 150px cut row 5 of the app chips through the middle and said nothing (half a "Music" chip, reported 2026-08-12), so `clampChips()` measures the real row height at render, keeps WHOLE rows inside 28% of the column, drops the rest into the overlay and counts them out loud ("+N more apps"); it skips the removal entirely below 1100px, where the page scrolls and there is no height to ration. That 28% is a CEILING, not the whole ration: it assumes the column has room to give, so `clampChips()` then sheds extra WHOLE rows while `col-actions` still overflows, and it re-runs on every `renderPageChips()` rebuild, not just on resize. Both halves are load-bearing — the Go to page chips land from the 10s `/api/phone` poll, LONG after the clamp last measured, and a ration that never re-ran had allowed 6 rows when only 5 existed, so nothing was dropped while the column ran 32px over. The Actions column's four fixed blocks sit above `#thread`, the ONE flexible track, so free height lands there instead of at the bottom of the card — but `#thread` is `flex:1 1 auto; min-height:0`, so it is also where an unrationed surplus lands: it shrank to 12px holding 60px of content and the column's `overflow:hidden` cut `#thread-note` through the middle, 31px of it gone at a 780px viewport with no "+N more" to say so (measured 2026-08-12, headless; clean at 720-1080 after the fix). Go to page renders chips 1..total from `/api/phone`, which reads `helpers.current_page()` ONLY when springboard is frontmost (0.37s on a 10s poll; inside an app there is no PageIndicator to find) and wraps it in `trust.internal()` — a bookkeeping poll that armed the send gate every ten seconds would be a gate nobody can turn off. There are no Today/Library chips because `goto_home_page()` refuses anything outside 1..total by design, but it still walks correctly OUT of both, so any chip escapes them and the readout names where you are. Gestures are `edgeSwipe` wrappers (no new endpoint) whose coordinates are MEASUREMENTS, not preferences: a system gesture that is too short or too fast is swallowed in silence, and Back at 45% width / 0.25s did nothing from Settings > General while the identical gesture at 91% / 0.6s popped the screen every time (device, 2026-08-12). A gesture button also BLURS itself on a pointer click: keys only reach the phone while nothing focusable holds focus (the window keydown handler returns early on `input,textarea,button,select,[tabindex]`), so a clicked button keeps focus and swallows every letter typed after it — Search opened Spotlight and then ate the search string, and the obvious repair, clicking the screen, sends a TAP that closes Spotlight. It blurs only when `ev.detail > 0`, because that is 0 for Enter/Space on a focused button and blurring there would throw a keyboard user out of the tab order. There is deliberately NO app-switcher button: the switcher needs a swipe that HOLDS before it lifts, `swipe()` is press-move-release with nothing in between, and two different shapes (0.9s and 1.4s) both left the phone where it was — it needs a press/pause/release chain in `wda_client` first. Thread is the read half of "Text someone" (`POST /api/read-thread` → `helpers.read_messages`, which shipped from the start with no human surface calling it): click-to-run and never a poll because it drives the phone for ~10s, behind a `withBusy('READING')` label; its feedback (empty contact, busy phone, read errors) renders in `#thread-note` directly under the button, NOT via `showHint` — `#click-hint` sits at the bottom of the phone pane two columns away, and a "Type a contact first." over there read as the button doing nothing (live 2026-08-14), bubbles rendered with `textContent` and degraded oldest-first to fit. It must NOT be wrapped in `trust.internal()` — the exact opposite of the page poll — because message text is the most direct injection route into anything sharing the process; the viewer's own Send stays ungated through `trust.human_initiated()`, an agent send from the debug console does not, and a test pins both directions; checks auto-open the overlay only on an ok→fail transition, once per page load, Unlock/Lock and Restart link buttons, red STOP/RESUME kill switch, red LAN-exposure banner (loud by default; probed in the background) (:8770, VIEWER_PORT to override; 8765 belongs to the Practical Systems API). All `/api/*` calls are origin-guarded against cross-site/DNS-rebinding. Deep sleep kills WDA (~15min after the screen darkens) and NOTHING over USB can wake the phone, so a watchdog thread self-heals: it polls `device.lockdown_ready()` and reruns `up()` the moment the human wakes the phone (cool-down guarded; `/api/unlock` names this exact move when the link is down instead of timing out). Gestures serialize through `_ACTION_LOCK`, but a gesture that cannot take it within `_ACTION_WAIT` (2s) is DROPPED with a 409, never queued: the lock is held 11s by an unlock from a fresh lock and 20-30s after a deep sleep, and a gesture that waits that long is no longer aimed at the screen the human saw. Measured 2026-08-11 before the fix: four taps made during one 11s unlock all executed AFTER it finished, 4.8-9.5s stale, landing on the unlocked home screen — that burst is what "runaway" looked like. The other half of the fix is the `busy` label on the phone pane (`withBusy`), because an unlabelled 20s freeze is what makes someone click again in the first place; clicks during it are answered locally and never sent. `/api/unlock` passes the viewer's own client into `helpers.unlock(c)` (unlock is timing-sensitive; no session re-discovery mid-wake). The viewer retunes the MJPEG stream whenever the session id changes; gesture waits ride with the shared session (see wda_client.py). A stationary hold is a LONG PRESS, not a tap: it fires on a local `LONG_PRESS_MS` (400ms) timer while the button is still down, so the phone's context menu opens during the hold instead of a second after release, and a filling ring is the only signal it registered (the device press itself takes `LONG_PRESS_SECONDS`, 0.8s, so the menu trails the ring). Moving past the same 8px that separates a tap from a swipe cancels it; once fired, `pointerup` sends nothing more. The Home button does what the PHYSICAL Home gesture does, and which of its two jobs it runs depends on what is frontmost (`_app_is_open`, one `active_app()` read; unknown falls back to the walk so it can never become a dead button): from an app it only leaves the app (`press_home()`, 0.77-1.49s end to end), and only a second press, with springboard already frontmost, walks to page 1 (`helpers.goto_home_page(1)`, ~2.5s from page 3, down from 10.75s). Both halves depend on `press_home()` waiting for the springboard: while it could return early, press 1 answered in 0.11s and press 2 then read a stale `active_app`, pressed home a second time and left the phone on page 3 (measured 2026-08-12, before that fix). Walking unconditionally was the first shape and it froze the phone for seconds behind a busy label just to minimise an app, which is most of what the button gets used for. It runs behind a `withBusy` label and must NOT be routed through `gesturePost`: that opens with a `phoneBusy()` guard, so nesting it inside `withBusy` makes the button set its own label, refuse it, and silently send nothing (shipped exactly once, 2026-08-12; a test now scans `viewer.html` for the nesting). The checks RE-RUN THEMSELVES while any of them fails (3s, 3s, 5s, 8s, 15s, then every 30s) and stop once green: `launch.py` opens the browser immediately and brings the link up in a background thread, so the first run always lands mid bring-up, and running once at page load froze that red result until someone clicked Refresh — which is exactly what "the checks are always yellow until I refresh" was. It must also STOP once green: a full run is ~2s of go-ios subprocesses plus a screenshot (measured), so `/api/doctor` also serves its last result while `_ACTION_LOCK` is held, same reasoning as `/api/status` and `/api/phone`. While `admin.bringing_up()` is true the header reads "Starting link…" with grey `wait` dots instead of a red count, and the overlay does NOT auto-open — that now takes TWO consecutive failing runs with no bring-up in flight, because one is how every boot legitimately starts. On a FIRST run the same auto-open lands on the setup wizard instead of the checks panel: `/api/status` reports `setup_done` (= `.state/wda_session` exists, i.e. WDA has ever come up here) and `app_dir`, a 📱 Setup guide button shows until it flips, and the wizard's five steps are driven by the same doctor results — only the current step shows its instructions, and a test pins every check name it waits on to `admin.CHECKS`, because a renamed check would strand that step at ▶ forever. `_kill_stale_viewer()` kills the old viewer WITHOUT `/T`: the tunnel and the forwards are CHILDREN of the launch.py that started them, so a tree kill there takes the phone link down as a side effect of restarting the UI, and `up()` is already past its "Already up" early return by then (measured 2026-08-12: 11 green checks, then a second launch left tunnel and WDA dead; `down()` is what stops those, by their own pid files). `/api/status` memoises `window_size()` but ALWAYS calls `orientation()` first (7.7ms): `window_size()` was the ONLY WDA request the endpoint made and `"input": True` is the claim that the link is alive, so serving the memo without asking the phone anything reported a healthy link over a dead one for the whole outage — and deep sleep kills WDA ~15min after the screen darkens, so that is the normal case, not an edge one. viewer.html HIDES `btn-up` ("Restart link") and `btn-fix` while input is true, so the lie also removed the two buttons that fix it. `orientation()` raises when WDA is gone (falling through to the go-ios pixel-size branch), heals an evicted session so `_tune_mjpeg` still sees the change, and doubles as the rotation guard. Two independent adversarial reviews caught it 2026-08-14; tests pin the dead-link and the rotation case. `loadStatus` and `loadPhone` return early while `document.hidden`: closing `screen.src` alone achieved nothing, because the 5s `loadStatus` re-ran `startStream()` on the very next tick (Chrome coalesces hidden-tab timers to 1s granularity, it does not stop them), so the ~334KB/s saving lasted about 5 seconds. `loadApproval` stays UNGATED on purpose — it is the send-approval safety gate, and it reads a local JSON file, not the phone.

## Commands

- Run everything: `python launch.py` (viewer opens immediately; `up()` runs in a background thread). Double-click equivalents: `sidetap.cmd`, or the Desktop/Start Menu **SideTap** shortcut (`scripts/install_shortcut.ps1` installs it, `-Startup` adds run-at-boot, icon in `assets/sidetap.ico`)
- Tests: `python -m pytest tests -q`
- Diagnose: `phone-harness doctor` (never guess at connection problems — run this)
- After a replug: the viewer's Restart link button, or `phone-harness up`
- Enable touch input (free Apple ID): `phone-harness fix-input`, then click Start in Sideloadly (mid-week: `phone-harness fix-input .state/profile.mobileprovision` skips Sideloadly; installs need the phone unlocked)
- Never miss the weekly re-sign: `phone-harness notify-expiry --install` (daily toast when <36h left)

## Rules

- Coordinates are points, not pixels. The UI tree and taps use the same units.
- Keep `wda_client.py` free of go-ios knowledge and `device.py` free of HTTP knowledge.
- New agent primitives go in `helpers.py` and must be added to `__all__` (mcp_server.py picks most of them up from its `_TOOLS` list — add there too if MCP-safe).
- No new runtime dependencies beyond `requests` and `mcp` without a stated reason.
- Driving the phone needs the user's hardware set up (docs/setup-windows.md); unit tests must pass without a phone.
